# 低功耗设计与验证（数据门控）

> 对应 需求 **能力点 5**（"协同物理设计团队完成…**低功耗设计**"）—— 协同区里此前唯一未做的一项。
>
> **方法来源**：既有项目的 `tb_tcu_gate.sv`（数据门控验证，参数字 + 双 DUT 并列的对比手法）。
> **但两个场景的门控机理不同，收益数字不能混用** —— 见 §4。

---

## 1. 门控点：三个候选里选一个（含排除理由）

| 候选 | 评估 | 结论 |
| --- | --- | --- |
| **lane 门控**（降级后闲置 lane 不翻转）| 读代码发现 `ucie_rdi_tx` 已是 `lp_data = '0` 初始化 + 只对 `lane_valid` 的 lane 赋值 —— **已隐式具备** | ❌ 无改进空间，排除 |
| **时钟门控**（L1 空闲关时钟）| 需改时钟树，引入跨域/时序风险；本机也无 ICG 单元的时序库 | ⏸ 不在本轮范围（但真实 UCIe 的 L1/L2 主路径正是它，见 §4）|
| **数据门控（选定）** | 实测代码发现真实浪费：`lp_valid = busy`，**空闲时输出本无意义，组合逻辑却仍无条件读 flit** | ✅ 选定 |

## 2. 实现

`rtl/phy/ucie_rdi.sv` 的 `ucie_rdi_tx`：

```systemverilog
parameter int DATA_GATING = 0;                      // 0=原版  1=门控
logic rd_en;
assign rd_en = (DATA_GATING == 0) ? 1'b1 : busy;
...
if (rd_en && lane_valid[l] && (nxt_ptr < FLIT_BYTES[7:0])) begin   // ← 门控条件
```

**为什么用参数字而不是 `ifdef`**：让**同一份 RTL 综合出两个版本**，从而能做功能等价对比
（手法取自 `tb_tcu_gate.sv`）。参数经 `ucie_link_pipe` → `ucie_d2d_top` **三层透传**。

**功耗观测量**（仅仿真，用 `ifndef SYNTHESIS` 包裹，不进综合）：
`tog_total`（全部周期翻转位数）、`tog_idle`（空闲周期翻转位数）、`idle_cycles`。

## 3. 验证结果（`make lowpower`）

**结构**：`for (genvar g = 0; g < 2; g++)` 起两个 `ucie_rdi_tx #(.DATA_GATING(g))`，同一激励。

```
[S1] 空闲期 + 上游 flit 每拍变化
     GATING=0  tog_idle = 646      GATING=1  tog_idle = 0     ← 空闲期翻转被完全消除
[S3] 真实传输期（16 笔随机 flit，每笔 8 拍）
     两版本逐拍功能等价，无 MISMATCH                            ← 门控不改功能

汇总：GATING=0  tog_total = 884   GATING=1  tog_total = 0      idle_cycles = 187（两边一致）
```

**两条判据各有各的用处**：

- **S1** 回答"门控**有没有用**"——省掉 646 次无效翻转
- **S3** 回答"门控**有没有害**"——功能逐拍等价
  **没有 S3 的省功耗数字是不可信的**：只报"翻转降了"而不证明功能不变，等于没做验证

## 4. 边界（必须与数字一起说）

**① 收益依赖场景**。S1 的 646 次翻转发生在"**空闲期上游仍在变**"的条件下。而真实链路里
`ucie_rdi_tx` 的 `flit` 来自 AFIFO 的 `rdata`，**AFIFO 空闲时 `rdata` 是保持的** ——
那种场景下门控收益取决于上游是否静止，而**本验证台未能可靠构造该激励**
（TB 的 `flit_changes` 观测量自身不可信，已撤除该判据，原因写在源码注释里）。
**所以这个数字证明的是"门控机制有效"，不是"真实链路一定省这么多"。**

**② 与数据源场景的机理不同**。既有项目的门控收益来自**数据稀疏**（INT8 推理 ReLU 后
30–60% 为 0 的负载特征）；本项目的门控点来自**空闲期的无效翻转**，收益来自**链路空闲占空比**。
**两者同为动态功耗优化，但触发机理完全不同，不能共用收益数字。**

**③ 未做的低功耗手段**：**时钟门控（ICG）** —— 这是真实 UCIe 的 L1/L2 主路径；
另有电源门控、多电压域、UPF 流程，均未实现。ICG 需要时序库的集成时钟门控单元
与时钟树改动，超出本 demo 的仿真环境范围。

## 7. 功耗数字：做到了什么程度（2026-10-11 补）

> **先给结论**：本机**能算功耗报告**（OpenSTA 内置 `report_power` —— **不需要 ptpx**），
> 但**做不出「可引用的真实功耗数字」**。卡点是**活动率反标不上**，
> 而反标失败的原因是**缺标准单元 Verilog 模型** —— 与 SDF 时序仿真**同一根因**。

### 7.1 做了什么

`flow/power.tcl` + `cd flow && make power`：

```
read_liberty   Nangate45（internal_power 2459 组 / leakage_power 2071 组）
read_verilog   综合后网表
read_sdc       ucie.sdc
read_vcd       waves/ucie_d2d_top.vcd                 ← 这一步标注数为 0（见 7.2）
set_power_activity  输入端口 / 内部节点 activity=0.2 duty=0.5（**假设值**）
report_power
```

**实测输出**（`ucie_d2d_top` 综合网表）：

| 类别 | Internal | Switching | Leakage | Total |
| --- | --- | --- | --- | --- |
| Sequential | 2.8642e-02 | 1.5466e-03 | 3.0523e-03 | 3.3241e-02 W（36.9%） |
| Combinational | 4.2617e-02 | 1.0033e-02 | 4.3039e-03 | 5.6954e-02 W（63.1%） |
| **Total** | **7.1252e-02** | **1.1580e-02** | **7.3590e-03** | **9.0191e-02 W** |
| 占比 | 79.0% | 12.8% | 8.2% | 100% |

### 7.2 ⚠ 为什么这个数字**不能当功耗指标**

**实测反标率只有 0.70%** —— VCD 反标上 **2320** 个引脚，而综合网表共 **331302** 个引脚
（83770 个 cell），其余 99.3% 仍用假设值：

```
VCD（RTL 仿真）信号名：  a_tx_valid / ACK_EVERY / lclk …        （RTL 层次名）
网表（综合后）信号名：   _23078_ / _23079_ … + DFF_X1 / NOR2_X1 （自动网名 + 工艺单元）
```

**两者只在顶层对得上**（2320 个引脚），内部节点全对不上。

**两个实测踩坑（都会静默给出错误结论）**：
1. **`-scope` 要填 VCD 的*顶层名***（`tb_ucie_top`），**不是** DUT 实例路径
   （`tb_ucie_top.u_dut`）—— 填错时输出 `Annotated 0 pin activities`；
2. **`set_power_activity` 必须在 `read_vcd` *之前*** —— 否则 `-global`
   假设值会覆盖实测值，现象是"`Annotated 2320` 但功耗数字与纯假设时**一模一样**"。

**换 SAIF 也解决不了**：本机其实齐活 —— Verilator 5.050 有 `--trace-saif`（能生成）、
OpenSTA 有 `read_saif`（能读）—— 但**根因不是文件格式，而是层次/命名对不上**：
SAIF 同样来自 RTL 仿真。真正的解法是**门级仿真的 VCD / SAIF**（网表层次），
那需要**标准单元 Verilog 模型**（本机只有 `.lib` / `.lef`）。

上表那个 **90.2 mW** 是"时钟准确（来自 SDC）+ 0.70% 实测 + 99.3% 假设"的**量级估算**
—— 可用于理解"内部功耗占 79%、组合逻辑占 63%"这类**结构特征**，
**不能引用为芯片功耗指标**。

**要拿到可引用的数字，需要**：**门级仿真的 VCD 或 SAIF** → 需要**标准单元 Verilog 模型**
（本机只有 `.lib` / `.lef`，没有单元 `.v`）；或商业功耗工具（ptpx / PowerArtist）配合 SAIF。

> 踩坑记录（Tcl 语法雷）：脚本里写 `"[!]"` 会被 Tcl 当成**命令替换** →
> `invalid command name "!"`。与本项目"注释里别写工具名"属同一类语法雷，已统一改用 `(!)`。

### 7.3 这一节的用法

| 能讲 | 不能讲 |

| 数据门控消掉多少次无效翻转（646 → 0，实测）+ 功能等价 | ❌ "我给链路省了 X% 功耗" |
