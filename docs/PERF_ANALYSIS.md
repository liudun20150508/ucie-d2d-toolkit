# 跨 die 访问代价分析（解析法，不依赖仿真器）

> **为什么用解析法而不是 gem5**：gem5 建模的是 core / cache / 一致性 / NoC / 内存控制器，
> 而本链路的瓶颈在 PHY 时序、RDI 字节扇出、flit 聚合、credit/重传——**两者建模对象不重合**。
> gem5 只能把整条链路压成"一段额外延迟 + 一个带宽上限"来消费，也就是它**消费**本文件的结论，
> 而不是**产出**它。本文件的每个数字都来自本机实测或明确标注的推导/假设。
>
> 数据来源标注：`[实测]` 本机跑出来；`[推导]` 按设计参数计算；`[假设]` 行业参考值（**不是本项目测的**）。

## 2. 延迟分析

### 2.1 跨 die 的延迟代价

```
跨 die 单次访问（读）  ≈ 960 ns
本地 DRAM 访问         ≈ 100 ns  [假设]
────────────────────────────────
延迟代价               ≈ 10×
```

**这就是 chiplet 的物理现实**：信号要出 die、过封装、进对端 die，再原路返回。
所以 chiplet 的架构原则从来不是"把跨 die 做成透明"，而是**让跨 die 传输尽量粗粒度、可摊销**。

### 2.2 960 ns 里都是什么（哪些能动、哪些不能动）

| 段 | 估算 | 是否设计相关 |
| --- | --- | --- |
| 测试台激励节奏（tb 的 `while` 握手循环） | 数十 ns | ❌ **测量环境开销，不是设计延迟** |
| pack 聚合等待（`IDLE_FLUSH = 4` 拍） | ~40 ns | ✅ 可降 |
| AFIFO 跨域（两级同步） | ~20–30 ns | ⚠️ 结构必需，仅能微调 |
| RDI 传输（5 UI × 7.5 ns） | ~37.5 ns | ⚠️ 由链路宽度决定 |
| B 侧解析（66B beat 需 5 拍 unpack） | ~50 ns | ✅ 可流水 |
| B→A 反向再走一遍 | ≈ 上述之和 | — |

**关键判断**：960 ns 的主体是**往返（RTT）× 两次穿越**，而不是某一级的逻辑深度。
这与 STA 的结论一致——关键路径是 −71.25 ns 量级，而往返是 960 ns 量级，**差一个数量级**。
**所以延迟优化该动"往返次数与聚合等待"，而不是"缩关键路径"。**

## 3. 吞吐分析（本节是重点）

### 3.1 单流效率：对齐损失在哪

一个数据 beat 在字节流里是 **66 B**，而字节流宽度是 **16 B/拍**：

```
66 / 16 = 4.125 拍  →  实际占 5 拍（末拍只用了 2 B，浪费 14 B）
```

`[推导]` 单流有效带宽：
```
64 B 有效数据 / (5 拍 × 10 ns) = 1.28 GB/s
```
与实测的 **50 ns/beat 完全吻合** `[实测]`。

**效率损失 36%**（1.28 vs 2.007 GB/s），来源有两处：
1. beat 的对齐损失（66 B 跨 5 拍，最后一拍半空）
2. 协议层 16 B/拍 < 链路 16 B/UI 的等效速率（100 MHz vs 133.3 MHz）

### 3.2 并发度：Little's Law 暴露的真瓶颈

要**掩盖**延迟、跑满带宽，在途数据量必须满足：

```
在途字节数 = 带宽 × 往返延迟
           = 2.007 GB/s × 960 ns
           = 1926 B  ≈ 1.93 KB
           ≈ 30 个 64B 事务
```

**而当前配置能提供多少在途？**

```
AXI outstanding 深度 = 4 笔（AXI_ID_W=4，OS_DEPTH=4）
在途字节数 = 4 × 64 B = 256 B
```

**缺口 = 1926 / 256 ≈ 7.5 倍。**

`[推导]` 由 4 笔在途所能达到的吞吐上限：

```
256 B / 960 ns = 267 MB/s
```

**也就是说：在当前 outstanding 配置下，吞吐上限只有峰值的 13%**
（267 MB/s vs 2.007 GB/s）——**瓶颈是并发度，不是链路带宽。**

> ⚠️ 这个数字成立的前提是"请求必须等上一次完成才能发下一次"。AXI 允许 outstanding，
> 所以真实上限取决于**上游 master 愿意保持多少在途**。但**本 IP 自己只给了 4 笔的窗口**
> （AW/AR FIFO 各 4 深），上游想更深也深不了 —— 这一点是 IP 的架构限制，值得记下来。

### 3.3 两个瓶颈的分离（诊断结论）

| 瓶颈 | 量级 | 后果 | 修法 |
| --- | --- | --- | --- |
| **并发深度不足** | 4 笔 vs 需要 30 笔 | 吞吐上限 **267 MB/s**（13%） | 加深 outstanding + 加宽 AXI ID |
| **单流对齐损失** | 1.28 GB/s vs 2.007 | 单流最多到 **64%** | 字节流加宽到 32 B/拍，或让 beat 与 flit 对齐 |

**这两个是独立的**：就算把并发做到 30 笔，单流那 36% 损失还在（因为 66B 跨 5 拍）。
反过来也一样。**要跑到接近 2 GB/s，两个都得改。**

## 4. 适用负载画像

综合延迟（~1 µs、10× 于本地）与带宽（2 GB/s、约 1/10 于本地），可以给出明确的适用边界：

| 访问模式 | 单次代价 | 判断 | 理由 |
| --- | --- | --- | --- |
| **大块顺序搬运**（DMA / 权重复制） | 延迟摊销到可忽略 | ✅ **适合** | 受带宽限制（2 GB/s），延迟被流水掩盖 |
| **预取 / 双缓冲** | 延迟被计算掩盖 | ✅ **适合** | 只要有足够计算重叠 |
| 中等规模批量读（≥ 数 KB） | Little's Law 可满足 | ✅ 适合 | 需配合足够 outstanding |
| **细粒度随机读** | 960 ns × N，无法摊销 | ❌ **不适合** | 延迟受限，吞吐崩到 267 MB/s |
| **细粒度随机写** | 1020 ns × N | ❌ **不适合** | 同上，且写还要等 B 响应 |
| **锁 / 原子操作** | 往返 ~1 µs 每次 | ❌ **灾难** | 同步原语对延迟最敏感 |
| 跨 die 缓存一致性流量 | 每行 ~1 µs | ⚠️ **需慎重** | 这是 CHI/CXL 一致性设计的核心难题 |

**一句话结论**：
> 这条链路适合**粗粒度、可预取、可并行**的数据搬运，不适合**细粒度、强同步**的访问。
> 这也解释了为什么 chiplet 方案通常把**大块数据放在跨 die**、把**同步与锁留在 die 内**。

## 5. 优化路线（按收益排序）

| 优先级 | 手段 | 预期收益 | 代价 |
| --- | --- | --- | --- |
| **P0** | **加深 outstanding**（4 → 16/32）+ 加宽 AXI ID | 吞吐 267 MB/s → **~1.9 GB/s**（接近峰值） | FIFO 面积、ID 位宽、AXI 接口需相应扩展 |
| **P1** | 字节流加宽 16 → **32 B/拍** | 单流 1.28 → ~2.0 GB/s（消掉对齐损失） | 面积、时序压力上升 |
| P2 | 降 `IDLE_FLUSH`（4 → 1~2） | 单事务延迟 −20~30 ns | 小事务时 flit 利用率下降 |
| P3 | AW 与首个 W 数据并行发出 | 单拍写 −数十 ns | B 侧需支持乱序配对 |
| P4 | 接收侧"边收边交付"（不等 beat 凑齐） | 读延迟 −4~5 拍 | 累加器逻辑复杂化 |
| P5 | 理想下限 | 由 RTT 决定（两倍穿越 + 训练开销） | — |

**P0 是压倒性的**：它把吞吐从 13% 拉到 ~95%，而其他项都是个位数到几十个百分点的改善。
**这也说明"先加深 outstanding"应该是这个 IP 架构迭代的第一步。**

## 6. 对设计的反推（这份分析告诉我们什么）

1. **架构决策的优先级被重新排序**：原本以为瓶颈在链路带宽（2 GB/s），
   实际瓶颈在**并发窗口**（4 笔）。**这是靠实测数字算出来的，不是拍脑袋定的。**
2. **延迟优化与吞吐优化是两条独立路线**：延迟靠减少往返/聚合等待，吞吐靠加深并发/加宽通路。
   混在一起谈会失焦。
3. **"带宽"这个词要拆开说**：链路带宽（2.007）、单流带宽（1.28）、并发受限带宽（0.267）
   是三个不同的数——**不提清楚哪个，讨论就没有意义**。
4. **该链路的产品定位**：适合做 die 间的大块数据通道（内存扩展、权重搬运、Stage 间张量传递），
   不适合承担一致性同步流量——**这正是为什么真实 chiplet 会用 CXL 管内存语义、
   用 UCIe Streaming 管数据流**。

## 7. 本分析的局限（如实声明）

- 延迟数字**含测试台激励开销**（§2.2 已标出），真机数字会更小；
- 本地 DRAM 基线是 `[假设]` 的行业量级，不是实测，只用于量级对比；
- 未做**实测的并发扫描**（需要用多笔 outstanding 的激励才能测出真实吞吐曲线）——
  这是后续值得补的实验；
- 未建模功耗/热，也未建模 PHY 误码率对有效带宽的折损（当前 demo 的 CRC 重传在正常误码率下影响 <1%）。

## 8. 带宽密度（shoreline bandwidth density）〔2026-10-11 补〕

> **为什么单列一节**：需求第 4 条「**精通** Chiplet D2D 互联的核心原理与设计方法…对 D2D 互联的
> **低延迟、高带宽密度、高可靠性**设计有**深入的工程实践经验**」。低延迟在 §2、吞吐在 §3，
> 而"**高带宽密度**"此前**没有任何量化** —— 本节补上。
>
> **口径来源**：UCIe 3.0 白皮书（官网公开 PDF）用的正是 **shoreline bandwidth density** 这个词，
> 且分两个维度：**linear（GB/s/mm，沿封装边缘每毫米）** 与 **areal（GB/s/mm²）**。
> 白皮书给出 3.0 相对 2.0 的倍数：**1.7–2× linear、1.3–1.6× areal**；**公开材料未给绝对值**。

### 8.1 为什么是"每毫米"，不是"总共多少 GB/s"

D2D 的物理约束不是面积，而是 **die 边缘（shoreline）** —— 信号必须从边缘的 bump 出去。
同样 1 TB/s，占 10 mm 边缘和占 2 mm 边缘是两个完全不同的设计。所以：

```
带宽密度（linear）= 总带宽 ÷ 占用的边缘长度
```

### 8.2 本 demo 的测算 `[推导]`

本 demo 的 RDI 抽象是「**每 lane 每 UI 传 1 字节**」，16 条数据 lane，`rdi_clk` = 133.3 MHz：

```
per-lane 速率 = 1 B/UI × 133.3 M UI/s  = 133.3 MB/s = 1.066 Gb/s（单向）
×16 lane 原始 = 16 × 1.066 Gb/s       = 17.07 Gb/s ≈ 2.13 GB/s
链路层有效    = 2.133 × 64/68          = 2.007 GB/s   ← 与 §1.1 实测一致
```

**边缘占用 `[假设]`**（本 demo 未建模物理 pitch，按公开的 UCIe 封装分级取参考值）：

| 封装分级 | bump pitch（参考） | 16 lane 占用边缘 | linear 密度 |
| --- | --- | --- | --- |
| UCIe-S（标准封装 2D） | ~110–130 µm | ~1.8–2.1 mm | **≈ 1.0 GB/s/mm** |
| UCIe-A（先进封装 2.5D） | ~25–55 µm | ~0.4–0.9 mm | **≈ 2.2–5.0 GB/s/mm** |

### 8.3 ⚠ 必须主动说清：本 demo 与真实 UCIe **不在一个量级**

**"1 B/UI per lane" 是抽象，不是真实电气**：

| | 本 demo | 真实 UCIe |
| --- | --- | --- |
| 每 lane 电气形态 | 抽象字节流 | **差分对** |
| 每 UI 有效载荷 | 1 字节 | **1 bit** |
| 单 lane 速率 | 1.066 Gb/s | 4 → 32 → **64 GT/s**（3.0） |
| 16 lane 总带宽 | 2.007 GB/s | 数十～上百 GB/s |

**所以本 demo 的密度数字只证明「方法会算」，不代表能达到真实 UCIe 的密度。**
讲解时这一点要**主动交代** —— 否则被追问"真实 UCIe 是几十 GB/s/mm，你 1 GB/s/mm 怎么解释"就答不上来。

### 8.4 敏感度：到底是什么决定密度（本节的核心结论）

| 杠杆 | 变化 | linear 密度 | 代价 |
| --- | --- | --- | --- |
| **lane 数** | 16 → 32 | **不变** ⚠️ | 边缘占用同比翻倍 |
| **单 lane 速率** | 1 B/UI → 2 B/UI | **×2** ✅ | 电气/时序压力 |
| **封装 pitch** | UCIe-S(110µm) → UCIe-A(40µm) | **×2.75** ✅ | 需先进封装 / hybrid bonding |

**三条推论（这才是架构层面的东西）**：

1. **堆 lane 数不提高 linear 密度** —— 它提高总带宽，但边缘同比增加。这也解释了为什么
   "x32 比 x16 快一倍"在密度视角下**毫无意义**；
2. **提高单 lane 速率才提高密度** —— 这正是 UCIe 1.0 → 3.0 走的路（4 → 32 → 64 GT/s）；
3. **换更细的封装 pitch 直接提高密度** —— 这正是 UCIe-A / UCIe-3D（hybrid bonding，
   pitch 9 µm → ~1 µm）的意义所在。

**结论**：所谓"高带宽密度设计"，工程抓手是 **① 拉高单 lane 速率（靠电气与均衡：3.0 的
3-tap TX FFE + RX CTLE + 可选 DFE）② 用更细 pitch 的封装 ③ 提高编码效率（少 lane 载同样带宽）**，
**不是"多堆 lane"**。

### 8.5 本 demo 在这条上的真实位置

| 维度 | 本 demo | 真实 UCIe 3.0 | 差距性质 |
| --- | --- | --- | --- |
| 单 lane 速率 | 1.066 Gb/s（抽象） | 64 Gb/s（NRZ 差分） | **电气层未建模** |
| 16 lane 总带宽 | 2.007 GB/s | 数十～上百 GB/s | 同上 |
| linear 密度 | ~1 GB/s/mm（UCIe-S 口径，`[假设]` pitch） | 比 2.0 高 1.7–2×（绝对值未公开） | 同上 |
| **密度优化手段** | lane 数 / 速率 / pitch 的**敏感度分析**（§8.4） | 电气均衡 + 细 pitch 封装 | **方法对、物理没做** |

**一句话**：本节给的是**"密度怎么算、被什么决定、往哪使劲"**的判据（可迁移到真实项目），
而不是"我做出了高密度链路" —— 后者需要 PHY 电气与先进封装，不在本 demo 范围（见 §7 局限）。
