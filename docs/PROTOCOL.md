# 协议层事务映射规格：AXI4 → UCIe flit

> 对应需求第 2 条：**"带领组员完成 UCIe 协议栈全链路的 RTL 设计与代码实现，
> 覆盖协议层、适配层和物理层的数字部分。其中，协议层优先支持 AXI、CHI 协议接口。"**
> 本文就是这条要求里"协议层"的设计规格。

---

## 1. 分层位置

```
AXI4 master ──▶ rtl/proto/ucie_axi_tx ──▶ ucie_dll ──▶ link_pipe ──▶ (对端)
                （协议层聚合）             （适配层/DLL）  （RDI/PHY 数字）
AXI4 slave  ◀── rtl/proto/ucie_axi_rx ◀── ucie_dll ◀── link_pipe ◀── (对端)
```

- **协议层（本文件）**：把 AXI4 事务聚合/序列化成字节流，装进 flit；反向拆解还原。
- **适配层（已有）**：`ucie_dll` 负责 flit 组包、CRC、ACK/NAK 重传、credit 流控。
- **物理层数字（已有）**：`ucie_rdi_*` + `ucie_afifo` + `ucie_ltssm`。

## 2. 字节流容器模型（本设计的核心取舍）

真实 UCIe 的 flit 是**协议层聚合容器**：上层多个协议包的字节被无缝拼接进 flit，
不要求包与 flit 边界对齐。本 demo 沿用这个模型：

| 项 | 设计 |
| --- | --- |
| flit 载荷 | `payload[0..63]` 共 **64 B，全部**是协议层字节流 |
| 填充 | 不足处填 `PAD_BYTE = 0x00`（即 `TXN_IDLE`） |
| 字节流接口宽度 | **16 B/拍**（对齐链路 16 B/UI @133 MHz ≈ 2.1 GB/s） |
| 流控 | 字节粒度：上游给 `in_bytes`，下游回报 `in_taken` |
| 带宽效率 | `64 / 68 = 94.1%`（flit 开销 = 2 B header + 2 B CRC） |

两个关键取舍（都是踩过坑才定下来的）：

1. **16 B/拍，而不是 1 B/拍。** 第一版把字节流接口写成每拍 1 字节，协议层吞吐
   就只有 100 MB/s，而链路有 2.1 GB/s —— 协议层会把链路饿死 16 倍。
2. **用 `PAD_BYTE` 而不是"有效字节计数字段"。** 计数字段要占掉 1 B，效率掉到 92.6%；
   靠"事务自描述 + IDLE 标记"可以全用 64 B。规则是：**在事务边界读到 0x00 即为 padding**，
   因为事务类型码里没有 0x00（`TXN_IDLE` 恰为空闲码），而数据区内部的 0x00 不受影响
   —— 解析器只在事务边界做这个判断。

数据 beat 在字节流里占 65 B（1 B beat 头 + 64 B 数据），不是 16 的倍数，
所以必然"吃掉半个 UI"：这正是字节粒度流控（`in_taken` / `out_taken`）存在的理由。

## 3. 事务格式

### 3.1 请求头（16B，所有 REQ 类事务共用）

| offset | 字段 | 说明 |
| --- | --- | --- |
| 0 | `txn_type` | 见 §4 类型表 |
| 1 | `axi_id[7:0]` | AXI ID（本 demo 物理上只接 4 位，高 4 位恒 0） |
| 2..9 | `addr[63:0]` | 小端（byte2 = addr[7:0]） |
| 10 | `axlen[7:0]` | burst 拍数 − 1 |
| 11 | `{3'b0, axburst[1:0], axsize[2:0]}` | 突发类型与每拍字节数（log2） |
| 12..13 | `tag[15:0]` | 事务标签，发送侧自增分配，响应原样带回 |
| 14 | `{6'b0, lock[1:0]}` | 保留（不支持独占访问） |
| 15 | `reserved` | 对齐到 16B |

### 3.2 数据 beat（66 B）

| offset | 字段 | 说明 |
| --- | --- | --- |
| 0 | `TXN_DATA = 0x03` | 类型码（**必须有**，原因见下） |
| 1 | `{4'b0, beat_idx[3:0]}` | 本 beat 在 burst 内的序号（0..15，对应 AxLEN 0..15） |
| 2..65 | `data[511:0]` | 64 B 数据（AXI 数据宽度 512 位） |

**为什么 beat 必须自带类型码**（本项目踩过的真实设计缺陷）：

第一版把 beat 定义成 `[beat_idx(1B)][64B data]`，想靠 beat 头区分。但 `beat_idx` 取值
0x00..0x0F，与事务类型码 0x01..0x05 **区间重叠** —— 接收侧在事务边界看到 0x01，
无法判断它是 `TXN_WR_REQ` 还是 `beat_idx=1` 的 beat；看到 0x00 又会被当成 padding 丢掉。
后果是**写数据一个 beat 都解析不出来**（仿真表现为 A 侧已发出、B 侧 `wr_data` 计数恒 0）。

加 1 B 类型码后，边界处首字节唯一确定事务种类，歧义消除，代价是每 beat 多 1 B
（开销 1/66 ≈ 1.5%）。这也解释了为什么真实协议（PCIe TLP / CXL）里**每个包都带自己的
头**，而不是靠"隐含的”上下文去猜包的边界。

### 3.3 响应头（16B）

| offset | 字段 | 说明 |
| --- | --- | --- |
| 0 | `txn_type` | `TXN_WR_RESP` 或 `TXN_RD_DATA` |
| 1 | `axi_id[7:0]` | 对应的 AXI ID |
| 10 | `axlen[7:0]` | 读数据事务：返回的拍数 − 1；写响应恒 0 |
| 11 | `{6'b0, bresp[1:0]}` | 写响应码（OKAY/EXOKAY/SLVERR/DECERR） |
| 12..13 | `tag[15:0]` | 回带请求的 tag |
| 14 | `{6'b0, rresp[1:0]}` | 读响应码 |
| 15 | `reserved` | |

`TXN_WR_RESP` 到此结束（无数据）；`TXN_RD_DATA` 后面按 §3.2 跟 N 个数据 beat。

## 4. 事务类型表

| 值 | 名称 | 方向 | 载荷 |
| --- | --- | --- | --- |
| `0x01` | `TXN_WR_REQ` | Master→Slave | 16B 请求头 |
| `0x02` | `TXN_RD_REQ` | Master→Slave | 16B 请求头 |
| `0x03` | `TXN_DATA` | 双向（数据 beat） | 66 B：[类型][beat_idx][64 B 数据] |
| `0x04` | `TXN_WR_RESP` | Slave→Master | 16 B 响应头 |
| `0x05` | `TXN_RD_DATA` | Slave→Master | 16 B 读数据头 + N 个 `TXN_DATA` |
| `0x00` | `TXN_IDLE` | — | 填充字节（接收侧解析时跳过） |

## 5. AXI4 支持子集（明确边界）

**支持**：

- 数据宽度 **512 位**（64B/beat），地址宽度 64 位
- 突发类型 **INCR** 与 **FIXED**；`AxLEN` 0..15（1..16 拍）
- **4 位 ID**；读/写各 **4 笔 outstanding**
- 写通道 AW 与 W **可乱序到达**（各自独立缓冲，按 tag 配对）
- 写响应 B、读数据 R 按请求顺序返回（in-order completion）

**不支持（本 demo 明确不实现，不做隐性假设）**：

- **WRAP** 突发类型、非 512 位数据宽度
- **LOCK / 独占访问**（exclusive）
- `AxCACHE` / `AxPROT` / `QoS` / `REGION` / `USER` 等属性信号（接口上不引出）
- **写数据交织**（AXI4 已废弃）、读数据乱序返回
- AXI4-Lite（未单独提供）

## 6. 响应匹配与顺序

- 发送侧为每个请求分配自增 `tag`，请求头携带；响应原样回带。
- 接收侧用 `tag` 匹配 outstanding 表项，用 `axi_id` 驱动 AXI 通道的 ID 语义。
- **顺序保证**：本 demo 的链路层是**有序可靠**的（累积 ACK + NAK 重传保证不丢不乱），
  所以跨 die 后事务顺序天然保持一致——这也是 D2D 链路相对通用网络的优势。

## 7. CHI 的边界（诚实声明）

CHI 是缓存一致性协议（REQ/RSP/DAT/SNP 四通道 + 一致性状态机 + snoop filter）。
本 demo 的做法是：

- **提供通道映射骨架**：`TXN_*` 类型表可扩展出 CHI 语义（REQ 读/写、RSP 响应、
  DAT 数据、SNP 侦听），字节流容器同样适用；
- **不实现一致性**：无 cache 状态机、无 snoop filter、无目录（directory）。

要在本 demo 上补 CHI，工程量的重心不在链路层（已具备），而在一致性协议本身——
这一点在讲解里应当明确区分："链路承载"与"一致性协议"是两件事。

## 8. 与真实 UCIe 的差异

| 项 | 本 demo | 真实实现 |
| --- | --- | --- |
| 协议层承载 | 自定义 AXI→flit 直接映射 | 多为 PCIe/CXL 栈或 Streaming，AXI/CHI 常作为 die 内主干经协议层聚合 |
| 有效字节描述 | payload 最后 1 字节计数 | 规范用 flit 级 valid 语义或固定打包规则 |
| 顺序 | 全序（依赖链路有序） | 可支持多虚拟通道（VC）与乱序 |
| 流控 | 单一 credit 池 | 按 VC/协议区分 credit |
