## 1. 微架构总览

### 1.1 数据通路与时钟域

```
                    lclk 域 (100 MHz, 10 ns)              rdi_clk 域 (133.3 MHz, 7.5 ns)
   ┌──────────────────────────────────────────────┐   ┌──────────────────────────────┐
   │  AXI slave 端口侧             协议层          │   │        物理层数字            │
   │  ┌──────────────┐  ┌───────────────────┐     │   │  ┌────────┐   ┌───────────┐  │
   │  │ ucie_axi_slv │→ │ ucie_stream_pack  │→────┼──▶│  │ AFIFO  │→  │ RDI TX    │  │
   │  │ _tx / _rx    │← │ ucie_stream_unpack│←────┼───│  │ (Gray) │←  │ (字节扇出)│  │
   │  └──────────────┘  └───────────────────┘     │   │  └────────┘   └───────────┘  │
   │           ↑                ↑                 │   │       ↑              ↓       │
   │  ┌────────┴────────────────┴──────────────┐  │   │  ┌────┴──────────────┐       │
   │  │            ucie_dll (适配层)            │  │   │  │  16 lane × 1B/UI │       │
   │  │  flit 组包/CRC · credit · ACK/NAK 重传  │  │   │  └───────────────────┘       │
   │  └───────────────────────────────────────┘  │   └──────────────────────────────┘
   │  ┌─────────────┐  ┌──────────────────┐      │
   │  │ ucie_ltssm  │  │ ucie_lane_repair │      │   ← 训练/映射（慢速控制通路）
   │  └─────────────┘  └──────────────────┘      │
   └──────────────────────────────────────────────┘
```

**两个时钟域异步**，只经 `ucie_afifo` 交互（`lclk_tx` / `rdi_clk` / `lclk_rx` 三个域完全独立建模）。
`[设计选择]` 刻意让测试台跑**异频**（100 / 133.3 MHz）而不是同频——同频会让 CDC 问题藏起来。

### 1.2 三个"速率"的关系（所有带宽决策的出发点）

| 层 | 宽度 | 频率 | 原始带宽 | 有效带宽 |
| --- | --- | --- | --- | --- |
| 物理层 RDI | 16 lane × 1B = **16 B/UI** | 133.3 MHz | 2.133 GB/s | 2.133 GB/s |
| flit 层 | 64B payload / 68B flit | — | — | × 64/68 = **2.007 GB/s** |
| 协议层字节流 | **16 B/拍** | 100 MHz | 1.600 GB/s | × 64/66（beat 开销）= **1.551 GB/s** |

**结论**：协议层（1.6 GB/s）< 链路层（2.0 GB/s），比值 **80%**。`[设计选择]`
协议层**故意**留出余量，因为字节流还要承载 16B 事务头、并且会遇到 pack 的 flush 抖动——
若两者取等宽，协议层会成为周期性瓶颈。这一条是"16 B/拍"而不是"8 B/拍"的依据：
早期版本用过 1 B/拍（=100 MB/s），会把链路饿死 16 倍 **[实测：见 README 坑清单 18]**。

## 2. 关键参数决策表

每个参数给出：取值 / 依据 / 备选取法 / 代价。**讲解时被问"为什么是这个数"，这张表就是答案。**

| 参数 | 取值 | 依据 | 备选与代价 |
| --- | --- | --- | --- |
| `LANES` | 16 | UCIe 标准封装 x16 module | x8 → 带宽减半；x32 → 面积与 PHY 复杂度上升 |
| `LANE_BYTES` | 1 B/lane/UI | 规范语义 | 加大需 PHY 配合 |
| `FLIT_PAYLOAD_BYTES` | 64 | 标准封装 flit 语义（68B 含头/CRC） | 256B 延迟优化 flit → 延迟↑、缓冲面积↑ |
| `FLIT` 传输 UI 数 | `ceil(68/16)` = **5**，末 UI 仅 4B 有效 | 68 与 16 不整除，必须按**字节**而非按拍描述有效 | 若强行按拍对齐，需加 padding → 带宽损失 |
| `LANES_TOTAL` | **17**（16 + 1 冗余） | 打坏 1 条 lane 仍能跑满 x16 | 无冗余 → 良率损失直接反映成出货率 |
| `MAP_W` | 5 bit | 物理 lane 编号 0..16 需要 5 bit | 用 4 bit → 冗余 lane 编号 16 被截断成 0 **[实测：踩过]** |
| `RETRY_BUF_DEPTH` | 8 | 覆盖一次 NAK 往返内能发出的 flit 数 **[推导]**：单程约 40–50 拍 ÷ 每 flit 5 UI ≈ 8–10 | 16 → 面积翻倍；4 → 吞吐骤降（会频繁等 ACK） |
| `CREDIT_INIT` / `CREDIT_MAX` | 8 / 32 | 与重传窗口同量级，保证发送侧不会"无谓等待" | 过大 → 接收侧缓冲压力；过小 → 链路空转 |
| `RETRY_TIMEOUT` | 48 拍 | > 一次 ACK 往返（约 100 拍的一半，配合累积 ACK 实际更快） | 太小 → 误触发重传；太大 → 真丢包时恢复慢 |
| `STREAM_W_BYTES` | **16 B/拍** | 对齐链路 16 B/UI **[设计选择]** | 8 B/拍 → 协议层仅 800 MB/s，成为瓶颈 |
| `STREAM_BYTES` | 64（payload 全用） | 靠"事务自描述 + IDLE padding"省掉有效计数字段 | 63B + 1B 计数 → 效率 92.6%（vs 94.1%） |
| `TXN_HDR_BYTES` | 16 | 地址 64b + len/size/burst + tag/ID，对齐 16B 便于解析 | 压缩到 8B → 字段不够，需要额外编码 |
| `DATA_BEAT_BYTES` | **66**（1B 类型 + 1B beat 头 + 64B 数据） | beat 头必须自带类型码（见 §5.1 的"区间重叠"缺陷） | 65B（不带类型码）→ 边界不可判，**实测跑不通** |
| `AXI_DATA_W` | 512（64 B/beat） | AXI 允许的最大常规宽度之一，一拍一个 flit 量级 best match | 256 → 事务数翻倍、头开销翻倍 |
| `AXI_ID_W` / `OS_DEPTH` | 4 / 4 | outstanding 4 笔（读写各 4） | 加深 → FIFO 面积↑；AXI ID 也需相应加宽 |
| `ACC_BYTES`（累加器） | 96 | = 66B beat + 16B UI + 余量，且是 16 的整数倍 | 太大 → 移位器面积/时序恶化；太小 → 卡死 **[实测：踩过边界]** |
| `CTRL_FIFO_DEPTH` / `RX_FIFO_DEPTH` | 8 / 4 | 控制 flit 可能突发（ACK+CREDIT 连发）；交付侧只需吸收短时反压 | — |
| `AFIFO` 深度 | 8（`ADDR_W=3`） | 2 的幂，Gray 码指针要求 | 16 → 面积↑；4 → 跨域抖动下易空 |
| `SKEW_MAX_UI` | 4（**已实现**） | per-lane deskew 补偿窗口上限 | 小于实测偏斜会被饱和截断；更大则缓冲与门数线性增长（见 `rtl/phy/ucie_deskew.sv`）|
| LTSSM 各阶段时窗 | SBINIT/MBINIT/LINKINIT 8 拍、MBTRAIN 16 拍 | 仿真收敛用的小值 **[设计选择]** | 真实值由 PHY 训练时间决定（µs 级） |

## 3. FIFO / 缓冲深度推导明细

深度不是"随手取 8"，每个都有来处。**表里的"覆盖目标"是可以拿到讲解里讲的**：

| 缓冲 | 深度 | 覆盖什么 | 不足时的症状 |
| --- | --- | --- | --- |
| AW FIFO | 4 | AXI 承诺的 4 笔写 outstanding | AW 通道被反压 → 上游 master 停顿 |
| AR FIFO | 4 | 同上（读） | 同上 |
| W skid | 1 | 吸收一拍 W 数据，避免 W 通道被源生成器节奏拖住 | W 通道空转，写带宽下降 |
| retry buffer | 8 | 一次 NAK 往返内发出的 flit（约 8–10 个） | 窗口满即反压上游，吞吐掉 |
| 控制 flit FIFO | 8 | ACK+CREDIT 可能连发（一拍最多入队 1 条，突发时需排队） | 队列满 → 反馈延迟 → 误触发超时重传 |
| RX 交付 FIFO | 4 | 上层 ready 的短时反压 | 丢数据（有 SVA 断言兜底） |
| AFIFO（×4） | 8 | 跨域突发 + 两级同步器的采样不确定性 | 空/满抖动 → 吞吐下降 |
| 字节流累加器 | 96 B | 66B beat + 16B UI + 余量（同拍"先追加后消费"需要额外空间） | 满了就不收 → **死锁** |
| pack 缓冲 | 64 B | 一个 flit 的载荷 | — |

**`[推导]` 重传窗口 8 的算法**：
```
单程延迟 ≈ 40–50 lclk 拍            （§6 实测分解）
一个 flit 占用链路 ≈ 5 UI × 7.5ns ≈ 37.5 ns ≈ 4 lclk 拍
NAK 往返 ≈ 2 × 单程 ≈ 80–100 拍
窗口内可发 flit 数 ≈ 100 / 4 ≈ 25  ← 理论上限
实际取 8：因为 ACK 是**累积**的、并且每收到一个 flit 就回 ACK（ACK_EVERY=1），
        实际在途 flit 数远小于理论上限；8 足以覆盖"ACK 在路上"的窗口而不浪费面积。
```
> 这段推导本身就是要展示的思路：**深度 = 覆盖往返，不是拍脑袋**。真实项目里会用链路 RTT 的实测值来算。

## 4. 逐模块微架构

### 4.1 `ucie_dll`（适配层 / Data Link Layer）

**结构**：唯一 `always_comb` 做决策 + 唯一 `always_ff` 做状态更新（避免多驱动与竞态）。
`[设计选择]` 这条纪律是刻意的：第一版把入队写在 `task` 里、又从两个 `always` 块驱动同一信号，
直接出多驱动 **[实测：见 README 坑清单]**。

| 子功能 | 微架构 |
| --- | --- |
| 发送 | `flit_tx` 组合组头 + CRC → `retry`（8 深窗口）→ 仲裁 → 链路 |
| 接收 | `flit_rx` 单深度 skid + CRC 校验 → seq 比较 → 交付 FIFO |
| 反馈 | 控制 flit FIFO（24 位条目 `{aux, arg, msg}`），一拍最多入队 1 条 |
| 仲裁 | **控制 flit 绝对优先**于数据 flit（同一 flit 通道）—— 保 ACK/NAK 的延迟敏感优先级 |
| 信用 | 发送扣 1、接收侧按交付返还（**搭载在 ACK 的 byte2**，省一条控制 flit）**[设计选择]** |
| 去重 | 序号"更旧"视为对端重传副本 → 重新 ACK 一次（避免对端白等超时） |

**CRC 的微架构**：`crc16_flit()` 是**组合展开**（66 字节 × 8 = 528 级异或链）—— 面积小。
~~但它是 WNS −71.25 ns 的主要来源~~ **（2026-10-11 订正：这句是错的** —— 三条违例路径
**都不经过 CRC**，真因是综合网表的**高扇出未缓冲**，见 §7.2 与 `BACKEND.md` §3.2）。
备选是逐字节流水（`rtl/link/ucie_crc16.sv` 已有骨架），代价是多 2–3 级流水寄存器和面积。

### 4.2 `ucie_link_retry`（重传窗口）

三段式：**组合算 next 值 → 时序统一更新**。关键设计点：

- 序号是 8 bit **回绕**的，窗口判断一律走模 256 区间函数 `in_window()`，
  **禁止用大小比较**（回绕序号最经典的坑）。
- 缓冲索引用 `ptr[$clog2(DEPTH)-1:0]`，指针本身 8 bit（支持回绕比较）。
- 超时重传：`inflight != 0` 且静默 48 拍 → 从 `ack_ptr` 整段重发。
- 断言 `a_window`：`inflight <= DEPTH` —— 回绕指针一旦算错，仿真立刻抓住。

### 4.3 `ucie_afifo`（CDC）

经典 Cummings 结构：二进制 + 格雷码双指针、两级同步器、深度取 2 的幂。

**一处刻意改写**：满判据**不用**教科书里的 `wbin_nxt = wbin + (winc & ~wfull)`——
那会让 `wfull` 依赖自身形成组合环（Verilator 报 UNOPTFLAT，综合工具也会告警）。
改成"自增候选 → 格雷码 → 判满" **[实测：踩过]**。

### 4.4 `ucie_ltssm`（链路训练）

10 个状态，`lclk` 域。三个实现要点：

1. **侧带握手 + 超时容错**：`stage_done()` = "对端 ACK 或计数到期，先到为准"——
   真实链路的侧带也会丢，超时兜底是必需的。
2. **重训计数在 ACTIVE 清零**：`rtry_q` 只在成功进入 ACTIVE 时复位。
   **[实测：踩过]** 不清零会让历史失败累积，第三次故障直接误判 TRAINERROR → L1。
3. **训练结果决定数据通路**：`valid_lanes` 少于一半 → TRAINERROR；否则进 LINKINIT。
   `link_active` 经一拍寄存后门控数据路径（避免与状态机组合耦合）。

### 4.5 `ucie_rdi_tx/rx`（字节 ↔ lane 扇出）

**TX**（`byte_ptr` 模型）：
```
每拍：从 flit 的 byte_ptr 起，给每条有效 lane 分 1 字节 → lp_data / lp_mask
      被 pl_trdy 接受后 byte_ptr += 本拍实际携带字节数
满 68B 结束；有效 lane 少时自动多用几拍（带宽换可靠性，无需改逻辑）
```
**这是"降级不丢数据"的实现基础**：lane 数减少只影响拍数，不影响正确性。

**RX**（组合累加）：
```
acc_c = acc_q；对每条有效 lane 且有 pl_mask 的字节：acc_c[cnt*8 +: 8] = data；cnt++
收满 68B → 交出完整 flit
```
`[设计选择]` 累加器是 **64B 移位寄存器**，面积不小但换来实现极简；
真实设计会改成"按 lane 写双口 RAM + 收齐就绪"。

### 4.6 协议层容器（`ucie_stream_pack/unpack`）

**字节粒度流控**是这一层的核心机制：
```
pack  : in_valid/in_data(16B)/in_bytes(1..16) → in_taken(0..16) 回报消费量
unpack: out_valid/out_data(16B)/out_bytes     ← out_taken  받接受消费回执
```
**为什么必须字节粒度**：一个数据 beat 是 66B，不是 16 的倍数，接收侧**必然**要"吃掉半个 UI"。
若接口只能整拍消费，接收侧就得多一层缓冲，复杂度反而更高。

**打包策略**：攒满 64B 立即发；上游空闲 `IDLE_FLUSH=4` 拍且缓冲非空 → 发部分 flit（尾部填 0x00）。
这一条是为延迟服务的：不为"凑满"而无限等待。

### 4.7 AXI 桥接（四个模块）

| 模块 | 微架构要点 |
| --- | --- |
| `slv_tx` | AW/AR 各 4 深 FIFO + 自增 tag；W 走 1 深 skid；**轮转仲裁**（`prio_q`）避免 AW/AR 饥饿；源生成器把请求/beat 展开成 16B/拍字节流 |
| `slv_rx` | 96B 移位累加器，**同拍"先追加后消费"**；靠 beat 头 bit4 的 RLAST 判 burst 结束（不依赖头里的 len，因为 AXI 的 R 通道不提供长度） |
| `mst_tx` | B 响应与 R beat 打包；**首拍带 16B 头 + 66B beat（82B）、后续只发 66B**；B 优先于 R |
| `mst_rx` | 同构累加器；`wlast` 由 `wbeat_q >= awlen_q` 推出（依赖 AW 先到，故**不支持写交织**） |

**四条共用的接口纪律**：`valid` 不依赖 `ready`（AXI 基本要求）；结构上"一个 `always_comb` 决策 + 一个 `always_ff` 更新"。

## 5. 关键设计取舍（含踩过的坑）

### 5.1 数据 beat 必须自带类型码（66B 而不是 65B）

第一版把 beat 定成 `[beat_idx(1B)][64B data]`，靠 beat 头区分。**但 `beat_idx` 取值 0x00..0x0F 与
事务类型码 0x01..0x05 区间重叠** —— 接收侧在事务边界看到 0x01，无法判断是新头还是 `beat_idx=1`
的后续 beat；看到 0x00 又当成 padding 丢掉。后果：**写数据一个 beat 都解析不出来** `[实测]`。

**代价对比**：

| 方案 | 每 beat 开销 | 边界可判性 |
| --- | --- | --- |
| 65B（无类型码） | 1B（1.5%） | ❌ 不可判 |
| **66B（带类型码）** | **2B（3.0%）** | ✅ 唯一确定 |
| 用 flit 头 fmt 区分 | 0B | ❌ flit 与 beat 边界无关，无法覆盖跨 flit 的 beat |

选 66B。**这条也解释了为什么真实协议（PCIe TLP / CXL）每个包都带自己的头**，
而不是靠"隐含上下文"猜包边界。

### 5.2 payload 全 64B 可用（不用有效计数字段）

| 方案 | 有效载荷 | flit 效率 |
| --- | --- | --- |
| 63B + 1B 有效计数 | 63 | 92.6% |
| **64B + IDLE padding** | **64** | **94.1%** |

敢用 0x00 当 padding 的前提：**事务类型码里没有 0x00**，且解析器**只在事务边界**做这个判断
（数据区内部的 0x00 不受影响）。

### 5.3 组合 CRC vs 流水 CRC

| 方案 | 面积 | 时序 | 现状 |
| --- | --- | --- | --- |
| 组合展开（528 级异或） | 小 | ~~WNS −71.25 ns~~ → **与 WNS 无关**（订正见 §7.2） | 当前实现 |
| 逐字节流水（2–3 级） | +寄存器 | — | **未实施**：违例根因是高扇出而非 CRC，该方案实测证伪 |

**保留组合版是有意的**：它让"功能正确 ≠ 时序收敛"这件事在项目里真实存在，而不是嘴上说说。
**但要分清**（2026-10-11 订正）：本项目真正把时序拉垮的是**高扇出未缓冲**（物理实现问题），
不是这处组合 CRC —— 这条链虽然长，却**没有落在任何一条违例路径上**（详见 §7.2）。

### 5.4 协议层与链路层的耦合方式

`[设计选择]` 协议层**不碰链路内部**，只通过 `ucie_dll` 的 64B 事务口对接：

```
ucie_axi_d2d_top
  ├── ucie_axi_slv_bridge ──┐
  ├── ucie_d2d_top          ├─ 64B 事务口（唯一的解耦面）
  └── ucie_axi_mst_bridge ──┘
```
**收益**：AXI 层增加只带来 **+3.0% 面积** `[实测]`，且换 CHI/PCIe 不用动链路一行。

## 6. 端到端延迟预算

### 6.1 实测数据 `[实测]`

测试条件：`lclk` 100 MHz（10 ns 一拍）、`rdi_clk` 133.3 MHz、链路已训练到 ACTIVE。
（`$time` 原始单位 ps，下表已换算为 ns。）

| 场景 | 起点 | 终点 | 延迟 |
| --- | --- | --- | --- |
| 单拍写 | AW 握手 | 收到 B 响应 | **1020 ns**（102 拍） |
| 单拍读 | AR 握手 | 收到 R 第 0 拍 | **960 ns**（96 拍） |
| 4 拍写 | AW 握手 | 收到 B 响应 | **1450 ns**（145 拍） |
| 4 拍读 | AR 握手 | 收到 R 第 0 拍 | **1240 ns**（124 拍） |
| 4 拍读 | AR 握手 | 收到 R 最后拍 | **1400 ns**（140 拍） |
| **读数据背靠背间隔** | R 第 N 拍 | R 第 N+1 拍 | **50 ns = 5 拍** |

### 6.2 分段推算 `[推导]`

以单拍写为例（102 拍），按设计参数逐段拆：

| 段 | 拍数 | 说明 |
| --- | --- | --- |
| tb 激励节奏 | 4–6 | tb 的 `while` 握手循环，每 beat 2 拍（**这部分不是设计延迟**） |
| A 侧 pack 聚合 + flush | ≤ 5 | 攒满即发；未满时等 `IDLE_FLUSH=4` 拍 |
| 进 AFIFO 跨域 | 3–5 | 写侧 1 拍 + 指针同步 2 拍 |
| RDI TX 传输 | 4 | 5 UI × 7.5 ns ≈ 37.5 ns |
| 出 AFIFO + DLL 交付 | 3–5 | 两级同步 + 累积 ACK 判定 |
| B 侧 unpack + mst_rx 解析 | 5–10 | 66B beat 需 5 拍 unpack + 累加器凑齐 |
| B 侧内存模型响应 | 2–3 | `wlast` → `b_go_q` → `bvalid` |
| **B→A 反向同样走一遍** | ≈ 40–50 | 上述之和 |
| **合计** | **≈ 100** | 与实测 102 拍吻合 |

**读数据的 5 拍/beat 间隔是关键结论**：它恰好等于"66B ÷ 16B/拍 = 4.125 → 5 拍"，
说明**连续读是带宽受限（back-to-back 饱和），不是延迟受限**。这正是流水线该有的样子。

### 6.3 延迟优化方向（按收益排序）

| 优化 | 预计收益 | 代价 |
| --- | --- | --- |
| pack 的 `IDLE_FLUSH` 从 4 降到 1–2 | 单事务 −20~30 ns | 小事务时 flit 利用率下降 |
| 协议层字节流加宽到 32B/拍 | 大幅提升吞吐（非延迟） | 面积、时序压力 |
| AW/AR 与首个 W 数据**并行**发出（不等 AW 完成） | 单拍写 −数十 ns | 需要 B 侧支持乱序配对 |
| 接收侧"边收边交付"（不等 beat 凑齐） | 读延迟 −4~5 拍 | 累加器逻辑复杂化 |
| AFIFO 深度加大 | 抑制抖动导致的偶发长尾 | 面积 |

> **讲解口径**：当前实现的延迟数字偏大（近 1 µs），**主要来自往返与聚合等待，而不是逻辑深度**——
> 分段表能证明这一点。真实产品会用 VC（虚拟通道）、credit 预分配、更激进的流水来压缩。

## 7. 面积与时序现状

### 7.1 综合（Yosys + Nangate45）`[实测]`

| 配置 | 单元实例（OpenROAD 展平后） | DFF | 说明 |
| --- | --- | --- | --- |
| 原 D2D 设计（`ucie_d2d_top`） | 189348 | 14920 | 链路 + 物理层数字 |
| + AXI 协议层（`ucie_axi_d2d_top`） | **317723** | **20992** | **协议层 +67.8%**（面积 371170 → 541568 µm²，+45.9%） |

> **口径（2026-10-11 复检订正）**：这里的"单元实例"是 **OpenROAD `link_design` 展平后**的
> `Number of instances`（`cd flow && make apr [TOP=...]` 的日志），不是网表文件里的行数——
> `build/syn/*_mapped.v` 是**层次化**网表（`ucie_d2d_top` 只有 12 个 `module` 定义），
> 文件内的实例行数是 83776，展平后才是 189348，两者**不是同一个口径**。
> 早期文档写的 "178823 → 184134（协议层仅 +3.0%）" 与现在实测的 189348 → 317723
> **方向一致但数量级不符**，已按实测订正。

**面积构成要点**：flit 位宽 544 bit 的寄存器阵列（retry 8×544、AFIFO 8×544×4）是 DFF 的主要来源。
真实设计应改为**双口 SRAM 映射**并单独做 MBIST —— 这是 §8 的微架构债。

### 7.2 时序签核（OpenSTA）`[实测]`

```
lclk 10.00 ns / rdi_clk 7.50 ns
worst slack max  = -71.25 ns      ← 纯 D2D 顶层（AXI 顶层 -71.32 ns，同一量级）
tns max          = -240878        ← 纯 D2D 顶层（AXI 顶层 -274041，新增逻辑带来更多违例路径）
worst slack min  = -0.04 ns       ← 保持基本满足
```

**根因（2026-10-11 订正）**：**不是**早先写的"CRC 528 级异或链 / RDI 字节 mux 全组合"，
而是综合网表的**高扇出未做缓冲** —— 网表内（排除时钟/复位）203 个 net 扇出 >100、最高 1100；
一个 559 扇出的 net 使 NOR4 单级延迟 11.362 ns（正常 0.1–0.2 ns）。
`lclk`（重传）−14.314 ns、deskew 的 `max_delay` 组 −40.776 ns 同源。详见 `BACKEND.md` §3.2。

**修复（APR 阶段）**：`repair_design` + `repair_timing -setup` 后
**WNS/TNS 均收敛到 0.00 ns**，面积 371170 → 381066 µm²（+2.7%）—— 未改一行 RTL。

### 7.3 WNS 优化路线图

| 步骤 | 手段 | 目标 | 验证方式 |
| --- | --- | --- | --- |
| 1 | CRC 改逐字节流水（`ucie_crc16.sv` 已备好骨架） | 砍掉最长链 | 重新 STA，看 WNS 变化 |
| 2 | RDI TX 的 `lp_data` 寄存输出（打一拍） | 切断 mux → RX 的长路径 | 同上 + 回归仿真确认功能不变 |

**每步都要回归 `make all` + `make test-axi`**——这就是"前端设计与时序收敛必须协同"的实证闭环。

## 9. 接口时序约定（跨模块纪律）

| 约定 | 内容 |
| --- | --- |
| 握手 | 两段式 `valid`/`ready`；**`valid` 不得依赖 `ready`**（否则形成组合环） |
| 复位 | 统一**异步低有效**（`always_ff @(posedge clk or negedge rst_n)`），避免 SYNCASYNCNET |
| CDC 复位 | 真实设计应加复位同步器；本 demo 未做（§8） |
| 断言 | SVA `disable iff (!rst_n)` 会被工具判为"同步使用"，用 `// verilator lint_off SYNCASYNCNET` 局部抑制 |
| 结构 | 每个模块**一个** `always_comb` 决策 + **一个** `always_ff` 更新 |
| struct 使用 | **不要按字段切数组元素**（`mem[i].field`）也不要嵌套字面量；一律"临时变量整体组装 + 整体读写" `[实测]` |
| 注释 | 不要以 `// verilator` 开头（会被当 pragma） `[实测]` |
